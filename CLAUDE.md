# Puzzle RPA — чат-бот с интерактивной визуализацией данных

## 1. О проекте

**Что строим:** чат-бот, которому руководитель пишет аналитический вопрос на русском и получает прямо в переписке живой дашборд — KPI-карточки, фильтры с поиском, переключатели разрезов и связанные графики. Дашборд можно дорабатывать диалогом, сохранять и возвращаться к нему.

**Контекст:** хакатон, кейс компании Puzzle RPA (ООО «ПУСК»). Кейс основан на реальном ТЗ; решения команд могут попасть в платформу заказчика. Сдаём репозиторий + живое демо + выступление.

**Дедлайн:** НЕ ОБЪЯВЛЕН на 2026-09-28. Пока не известен — сборка идёт вертикальными срезами, чтобы демо было готово в любой день.

**Целевая аудитория:** руководители и менеджеры крупной компании. Не аналитики: SQL не знают, в BI-систему ходить не хотят, решение принимают здесь и сейчас. Формулируют на естественном языке, не кодом.

**Боли, которые закрываем:**
1. Ad-hoc вопрос требует похода в BI и заранее построенного отчёта → бот сам находит данные и собирает дашборд по тексту запроса.
2. Нужной метрики в готовых отчётах нет → вычисления добавляются диалогом поверх выгруженной таблицы, без нового похода в базу.
3. Результат анализа теряется между сессиями → дашборд сохраняется целиком и восстанавливается в том же виде.

**НЕ входит в текущий этап (scope guard):**
- Реальные корпоративные системы заказчика — работаем только с тестовым датасетом.
- Сложная система прав доступа.
- Дашборды из 10+ графиков — целимся в 4.
- Совместная работа над дашбордом в реальном времени.
- Голосовой ввод, мобильные пуши, аналитика использования.

**Планка качества:** минимальные требования кейса (MVP) планкой не считаем — их закроют все команды. Целимся в «Целевой результат» и блок «сверх MVP». При этом порядок сборки всё равно снизу вверх: сначала рабочий сквозняк, потом наращивание.

Полный текст требований — `docs/CASE.md`. Описание датасета — `docs/DATA.md`.

## 2. Стек и архитектура

**Принципы (что незыблемо):**
- **Один API на все клиенты.** Веб и iOS — тонкие клиенты одного HTTP API. Никакой бизнес-логики в клиенте.
- **Центральный объект — сессия анализа**, а не график и не сообщение. Сессия = плоская таблица + стек вычислений + конфиг дашборда.
- **Вычисления не в SQL.** Данные выгружаются один раз, все расчёты идут поверх таблицы (прямое требование кейса).
- **Вычисления — стек шагов, а не мутация таблицы.** Иначе «отмени» и «поменяй формулу» невозможны.
- **Интерактив не ходит в LLM и не ходит в БД.** Фильтры, переключатели, зум считаются на клиенте поверх уже выгруженной таблицы.
- **Генерируемое моделью не исполняется напрямую.** SQL — только read-only одиночный SELECT с таймаутом; формулы — типизированные операции, не eval.
- **Цифры честные.** Неполный период, пустая выборка, разное зерно плана и факта — обрабатываются явно, а не молча.

**Стек по слоям:**
| Слой | Технологии | Хостинг |
|---|---|---|
| Backend | Python 3.12, FastAPI, pandas, Pydantic | локально / Docker |
| Данные | PostgreSQL 16 (данные — read-only роль; дашборды — схема `app`) | локально / Docker |
| NL-слой | OpenAI API | внешний |
| Web | React + TypeScript + Vite, Plotly.js | локально / статика |
| iOS | SwiftUI + WKWebView (дашборд переиспользует веб-рендер) | симулятор / устройство |

**Почему Plotly, а не ECharts:** в реальном ТЗ заказчика — Plotly. Совпадение со стеком заказчика на защите дороже, чем выигрыш ECharts в тач-UX, который мы всё равно допиливаем руками.

**Почему PostgreSQL, а не ClickHouse:** датасет 180k строк фактов, нужны джойны шести таблиц. Колоночная СУБД здесь не даёт ничего, кроме усложнения.

Высокоуровневая схема — `docs/ARCHITECTURE.md`. Решения с альтернативами — `docs/adr/`.

## 4. Порядок сборки продукта

Вертикальными срезами: после каждого есть что показать.

1. **Срез 0 — фундамент.** Postgres поднят, CSV загружены, схема с индексами, read-only роль. Скелет FastAPI.
2. **Срез 1 — сквозняк.** Вопрос → план запроса → SQL → плоская таблица → один график → отображается в веб-чате. Самый важный срез: с этого момента продукт существует.
3. **Срез 2 — таблица и вычисления.** Показ таблицы, стек шагов, добавление колонки по тексту, откат и правка формулы, видимая история.
4. **Срез 3 — дашборд.** 4 связанных графика, единый визуальный язык, KPI-карточки, перестройка графиков после вычислений.
5. **Срез 4 — интерактив.** Фильтры с поиском и мультивыбором, каскад регион→точка, переключатели разреза/метрики/периода/вида. Всё на клиенте, мгновенно.
6. **Срез 5 — сохранение.** Сохранить/открыть/переименовать/копировать/удалить, список с поиском и сортировкой, точное восстановление состояния.
7. **Срез 6 — умный бот.** Уточняющие вопросы при нехватке данных, текстовое резюме с инсайтами, обработка пустых выборок и неполных периодов.
8. **Срез 7 — iOS.** SwiftUI-оболочка поверх того же API, дашборд в WKWebView.
9. **Срез 8 — сверх плана.** Скачивание HTML/CSV, история версий, шаблоны запросов, синхронный зум.

**Что первично:** API-first. Сервер ведущий, клиенты подключаются по очереди. Веб-дашборд с первого дня адаптивный — иначе iOS превратится во второй продукт.

## 5. Глубина рассуждений — сколько думать перед действием

Не думать одинаково над всем. Уровень усилий выбирается по цене ошибки и обратимости:

| Класс задачи | Как действовать | Планирование |
|---|---|---|
| **Тривиальное** (опечатка, переименование, правка строки, известный паттерн) | Сразу делаю, без прелюдий | Не нужно |
| **Локальная фича / понятный баг** | Коротко проверяю окружение (как сделано рядом) → делаю | План в голове; TODO-список если >3 шагов |
| **Фича на несколько файлов / новый модуль / затрагивает API-контракт** | Сначала план, потом код. Читаю смежный код и `CONTEXT.md` перед стартом | Явный план + TODO-лист |
| **Архитектурное решение / необратимое / много вариантов** | Проектирую дважды: минимум 2 подхода, выбираю с обоснованием. Спорное — фиксирую в ADR | План-режим, при неясности — вопрос пользователю |
| **Диагностика неочевидного бага** | Гипотезы → проверка каждой → фикс. Не гадать, не «менять наугад» | Цикл гипотеза→эксперимент→вывод |

**Правила поверх таблицы:**
- **Есть достаточно данных — действую.** Не пересказываю варианты, которые не буду делать, не переспрашиваю то, что видно в коде.
- **Спрашиваю только то, что реально решает пользователь** — развилки в требованиях, а не выбор с очевидным дефолтом. Выбор с дефолтом — беру дефолт, называю его, иду дальше.
- **Необратимое и внешнее — подтверждаю до, а не после.** Удаление, перезапись, публикация, отправка наружу, деструктивный git. Разрешение в одном месте не переносится на следующее.
- **Перед удалением/перезаписью смотрю на цель.** Если содержимое противоречит тому, как его описали, — сообщаю, а не выполняю.
- **Не изобретаю преждевременных абстракций.** Обобщаю на третьем повторении, не на первом.

## 6. Как агент ведёт работу

- **Читаю перед тем как писать.** Перед работой в области — соответствующий `CONTEXT.md` (глоссарий) и релевантные ADR. Файлов нет — молча продолжаю, не флагаю их отсутствие.
- **Многошаговое — через TODO-лист:** в работе один пункт за раз, отмечаю выполненным сразу по факту.
- **Пишу код в стиле окружения:** имена, идиомы, плотность комментариев — как в соседних файлах.
- **Проверяю результат, а не только «скомпилировалось».** Нетривиальную правку прогоняю по реальному сценарию, прежде чем сказать «готово».
- **Отчитываюсь честно.** Тесты упали — говорю прямо с выводом. Шаг пропустил — говорю. Сделано и проверено — говорю без хеджирования.
- **Использую скиллы вместо импровизации**, когда задача под них подходит (раздел 10).

## 7. Как и куда записывать знания (обязательно)

Цель — чтобы знание из разговора не терялось и следующий агент не переоткрывал его заново.

| Что появилось | Куда пишем |
|---|---|
| Новый доменный термин | `CONTEXT.md` той области (формат — 7.1) |
| Паттерн / баг+фикс / gotcha / решение по коду | `{область}/CLAUDE.md` |
| Архитектурное решение с альтернативами и последствиями | новый файл в `docs/adr/` |
| Общее для всего проекта (стек, стиль, дедлайны, порядок работы) | этот файл |
| Факт про датасет (зерно, диапазон, аномалия) | `docs/DATA.md` |

**Когда писать:** сразу после каждой новой фичи, изменения поведения, найденного бага/решения или важного паттерна — не откладывать и не ждать отдельной просьбы.

**Как писать, чтобы дока не расходилась с кодом:**
- Правка меняет уже описанное поведение → **править/удалять старый текст**, а не дописывать рядом.
- В корневом `CLAUDE.md` детали не дублировать — достаточно упомянуть, что фича реализована.
- Формулировать конкретно: не «поправил сборку», а «X падает потому что Y; фикс — Z».
- Писать только то, что **не** выводится из кода и git.

### 7.1. Формат CONTEXT.md (глоссарий домена)

```md
# {Название области}

{Одно-два предложения: что это за область и зачем.}

## Language

**{Термин}**:
{Что это ЕСТЬ, одно-два предложения. Не что делает — чем является.}
_Avoid_: {синонимы, которые НЕ используем}
```
Правила: один термин на концепт, остальные в `_Avoid_`; только термины домена; определения короткие.

### 7.2. Формат ADR

```md
# ADR-{NNNN}: {Заголовок решения}

Status: {proposed | accepted | superseded by ADR-XXXX}
Date: {YYYY-MM-DD}

## Context
## Decision
## Consequences
```
Если новый вывод противоречит принятому ADR — не переопределять молча, а указать: «противоречит ADR-XXXX, стоит переоткрыть потому что…».

## 9. Стиль работы

- **Общение** с пользователем: на русском, неформально, коротко и по делу.
- **Код без комментариев «что делает функция»** — имена должны говорить сами.
- **Интерфейс продукта — полностью на русском.** Подписи осей, заголовки, легенды, названия метрик, сообщения бота. Английский остаётся только в коде.
- **Выбор технологий** — под аудиторию: заказчик автоматизирует ФНС, 1С и банки; при прочих равных предпочитаем то, что не требует VPN и не ломается в изолированном контуре.
- **Git:** коммитить и пушить только по просьбе. Стейджить конкретные файлы по имени, не `git add -A`. Ветка перед работой, если на дефолтной. Формат сообщений — Conventional Commits.
- **Секреты только на сервере.** Ключ OpenAI живёт в `.env` бэкенда, никогда не уходит в клиент и не попадает в `VITE_*` переменные.
