# Backend — знания области

Домен и термины — `CONTEXT.md`. Архитектура и решения — `../docs/ARCHITECTURE.md`, `../docs/adr/`. Факты о данных — `../docs/DATA.md`.

## База данных

Postgres 16 в Docker, порт **5433** (на 5432 у Родиона висит локальный Postgres). Поднимается одной командой, данные заливаются при первой инициализации из `db/seed/`.

**Две роли, и это граница безопасности, а не оформление ([ADR-0004](../docs/adr/0004-safe-generated-code.md)):**
- `bi_reader` — под ней исполняется всё, что построено из запроса пользователя. `default_transaction_read_only = on` + `statement_timeout = 10s`. Проверено: DELETE, UPDATE, CREATE TABLE и доступ в схему `app` отбиваются, `pg_sleep(30)` снимается по таймауту.
- `app` — владеет схемой `app` (сохранённые дашборды), данные только читает.

`default_transaction_read_only` сильнее, чем `REVOKE`: отбивает и DDL тоже, одним правилом вместо перечисления прав.

## Паттерны

**`plan_fact_flat` — единственный источник чисел для дашборда.** Вьюха на зерне `месяц × точка × продукт` с присоединёнными регионом, городом, типом точки и категорией. Сборщик SQL группирует её с фильтрами и ничего не джойнит руками. Обе ловушки джойна закрыты конструкцией:
- `sales_monthly` (materialized) поднимает факт до зерна плана **до** соединения — иначе `plan_amount` размножается по числу продаж на ключ (их до 4: разные договоры и клиенты).
- `plan_fact_monthly` соединяет через `FULL OUTER JOIN` — `INNER` выбросил бы 11 711 ключей с планом на 445 млн ₽ без продаж и поднял выполнение с 82,7% до ~92,7%.

`sales_monthly` материализована: данные статичны, пересчитывать нечего. Если данные обновятся — `REFRESH MATERIALIZED VIEW CONCURRENTLY sales_monthly` (уникальный индекс под это есть).

**`fact_horizon` — обязательный участник любого сравнения плана с фактом.** Отдаёт `2026-09-30` / `2026-09-01`. Без обрезки плана по горизонту 2026 год показывает 65,4% выполнения; с обрезкой — 89,4%, в одном ряду с 2023–2025. Первая цифра выглядит правдоподобным отставанием, поэтому особенно опасна.

## Баги и фиксы

**`initdb: invalid locale settings` при старте контейнера.** Ставили `LANG: ru_RU.utf8` — в образе `postgres:16` такой локали нет, генерируются только `C` и `en_US`. Фикс: убрать `LANG`, задать коллацию через ICU — `POSTGRES_INITDB_ARGS: "--locale-provider=icu --icu-locale=ru-RU --encoding=UTF8 --locale=C.UTF-8"`. Побочный выигрыш: правильная русская сортировка в фильтрах (`Ананас < ёж < Ёлка < Яблоко < Zebra`), а не побайтовая.

## Gotchas

- **`COPY` и `\N`.** В CSV датасета NULL закодирован как `\N`. У `FORMAT csv` дефолтный NULL — пустая строка, поэтому нужен явный `NULL '\N'`, иначе `closed_date` и `discontinued_date` упадут на приведении типа.
- **Порядок загрузки продиктован внешними ключами:** regions → products → clients → outlets → contracts → sales → sales_plan → discounts.
- **Два разных «региона».** `outlets.region_id` — где продали, `clients.region_id` — откуда клиент. Это не синонимы; какой имеется в виду, должно быть явно в спецификации выборки.
- **`inn` — text, не число.** Ведущие нули значимы.
