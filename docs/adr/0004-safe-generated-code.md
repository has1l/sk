# ADR-0004: Генерируемое моделью не исполняется напрямую

Status: accepted
Date: 2026-09-28

## Context

Кейс ставит это отдельным требованием: «не позволяйте генерируемому коду делать лишнее (удалять, изменять данные, ходить в сеть)» и «код не должен исполняться бесконечно».

В системе два места, где текст пользователя превращается в исполняемое: SQL-выборка и формула вычисления. Очевидный путь — попросить модель написать SQL и Python-выражение и выполнить их. Для SQL это означает доверять модели не написать `DELETE`; для формул — `eval()` над строкой от внешнего источника, то есть произвольное исполнение кода по запросу пользователя.

Промпт «пожалуйста, только SELECT» — не граница безопасности, а просьба.

## Decision

**Модель не производит исполняемый текст. Она производит структуру, которую исполняет наш код.**

SQL:
- Модель возвращает спецификацию выборки (разрезы, метрика, период, зерно, фильтры), SQL собирается нашим кодом с параметрами.
- Отдельная роль PostgreSQL только на чтение, без прав на запись и DDL.
- `statement_timeout` на соединении; жёсткий `LIMIT`.

Формулы:
- Типизированные операции из закрытого списка (ADR-0002).
- «Произвольная формула» разбирается собственным парсером арифметики: числа, четыре действия, скобки, ссылки на существующие колонки. Ни вызовов функций, ни атрибутов, ни импортов. `eval` не используется нигде.
- Деление на ноль даёт пустое значение, а не исключение.

## Consequences

- Класс уязвимостей закрыт конструкцией, а не проверками: нельзя выполнить то, для чего нет представления.
- Парсер арифметики — код, который надо написать и покрыть тестами. Примерно полдня, и он же даёт человекочитаемое отображение формулы в истории вычислений.
- Пользователь ограничен закрытым списком операций. Все примеры из кейса покрываются; если понадобится что-то за их пределами — добавляется операция, а не открывается исполнение.
- На защите это конкретный ответ на вопрос про безопасность вместо «мы просим модель вести себя хорошо».
