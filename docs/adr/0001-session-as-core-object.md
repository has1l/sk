# ADR-0001: Сессия анализа как центральный объект

Status: accepted
Date: 2026-09-28

## Context

Кейс описывает не разовый запрос «текст → график», а диалог: пользователь просит таблицу, добавляет вычисления, перестраивает графики, фильтрует, сохраняет и возвращается. Между репликами что-то должно жить. Вопрос — что именно считать единицей состояния.

Рассмотрено два подхода:

1. **Состояние в истории сообщений.** Каждая реплика порождает новый артефакт, контекст восстанавливается пересказом переписки в модель. Просто на старте, но: перестройка графика требует заново понять, что было построено; «отмени вычисление» не выражается; сохранение дашборда превращается в сохранение куска переписки; расход токенов растёт с длиной диалога.
2. **Явный объект состояния.** Диалог только меняет объект, а рендер читает объект.

## Decision

Центральный объект — **сессия анализа**: `спецификация выборки + плоская таблица + стек вычислений + конфиг дашборда`. Сообщения чата — команды, меняющие сессию, а не носители состояния.

Дашборд — это сериализованная сессия. Сохранение и восстановление — сериализация и десериализация одного объекта.

## Consequences

- «Перестрой третий график», «отмени вычисление», «сохрани» выражаются как операции над полями сессии — их не нужно изобретать заново для каждой реплики.
- Модель получает компактное описание текущего состояния вместо всей переписки: стабильная стоимость запроса независимо от длины диалога.
- Появляется обязанность держать сессию консистентной: изменение таблицы обязано инвалидировать зависимые части конфига (график ссылается на колонку, которую откатили).
- Сохранение хранит рецепт, а не данные — дашборд при открытии пересобирается на актуальных данных. Обратная сторона: если данные изменились, старый дашборд покажет новые цифры. Для нашего статичного датасета это не проблема, но это осознанный размен.
